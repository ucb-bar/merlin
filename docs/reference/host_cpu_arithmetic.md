# Shared host CPU arithmetic

Host implementations are selected by the host CPU contract independently of
the accelerator. A backend delegates shared host arithmetic to Merlin and
retains its own device instruction selection and physical ABI bridge. Reusing
the same host does not require regenerating these implementations for each OOT
compiler. Portable source arithmetic and native upstream lowering remain
separate existing paths.

`SourceFmaPairCapability` emits two independent source FMAs.
`SourceFmaBatchCapability` implements the explicitly permitted eight independent
finite FMA chains in `SourceFmaBatchContract`. The available CPU profile requires
explicit RV64GC/lp64d selection. Early-clobber constraints protect live inputs
belonging to other lanes. Source operand order, one rounding per result, gradual
underflow and the supplied effects permissions remain mandatory.

`emit_fixed_outward_f64_header` emits directed binary64 add/product operations
and optional directed binary32 conversion for the explicitly selected host.
It uses instruction rounding fields without changing the source rounding
environment. Narrowing and exact-bound hooks remain separate explicit options.
Late or duplicate activation refuses native compilation.

The symbol namespace is a validated C identifier. It changes symbol binding,
not source policy or CPU selection. Existing target bindings can therefore
delegate while retaining their generated bytes and ABI.

These APIs do not derive or prove the actual host ISA, source permissions,
nontrapping effects or unobserved exception flags. Callers must establish those
facts independently and bind the emitted source, compiler options and actual
objects in ordinary compilation. Unsupported CPUs and incomplete permissions
refuse; neither a capability record nor compilation success grants runtime
qualification or an accuracy waiver.

Native controls inspect actual objects for the selected FMA lane count and
fixed rounding without rounding-CSR changes, and exercise rejected capability,
symbol, activation-order and effect selections. They establish emission and
refusal behavior, not device timing, whole-model accuracy or performance parity.

`cpu_softmax` provides an explicitly selected Torch 2.10 FP32 CPU schedule:
SLEEF exponential arithmetic, eight-lane sums and reciprocal multiplication.
Its finite-input contract is required. The optional `maximum_policy="finite"`
uses a maximum operation with the same finite results and simpler NaN handling;
the default retains the source maximum. `build_cpu_softmax_maximum` exposes
that scalar choice separately so a provider can retain its original libm,
summation and division operations. Selecting the Torch schedule changes
arithmetic relative to sequential libm softmax and requires full-output
qualification.

This shared support contains no accelerator encoding, model selector, device
schedule, validation shape roster or reference performance calibration. It does
not automatically change the admitted tools or library grants in an authoring
experiment. Those remain controlled by the experiment's existing access rules.
