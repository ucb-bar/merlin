# SmolVLA FP8 NPU Kernel Workstream

End-to-end flow: export SmolVLA in per-tensor FP8 E4M3 quantization, compile
through IREE with custom NPU passes, generate NPU kernels via AutoComp, and
test on the npu_model cycle-accurate simulator.

## Quick Start

```bash
# 1. Setup
conda activate merlin-dev
uv run tools/merlin.py setup submodules --submodules-profile core --submodule-sync

# 2. Build compiler (with NPU plugin)
uv run tools/merlin.py build --profile npu --config release \
  --no-build-python-bindings --no-enable-libbacktrace

# 3. Export SmolVLA in pure FP8 (302 linears, zero int8)
uv run models/smolVLA/export_smolvla.py --mode fp8-po2 --device cuda

# 4. Compile (NPU plugin: QDQ fold + f32 elimination, no ISA lowering)
uv run tools/merlin.py compile models/smolVLA/smolVLA.q.fp8po2.mlir \
  --target npu_ucb --quantized --compile-to global-optimization --dump-phases

# 5. Demote remaining f32 → bf16
build/host-merlin-release/tools/iree-opt --iree-plugin=npu \
  --demote-f32-to-bf16 --canonicalize --cse --allow-unregistered-dialect \
  phases/module.4.global-optimization.mlir -o phases/module.5.demoted.mlir

# 6. Verify (should print PASS)
uv run benchmarks/SaturnNPU/scripts/verify_fp8_bf16_dtypes.py \
  phases/module.5.demoted.mlir

# 7. Extract kernels
uv run benchmarks/SaturnNPU/scripts/extract_all_kernel_variants.py
```

## Quantization

Per-tensor FP8 E4M3 with power-of-two scaling, adapted from the pi0-quant
project (`CompGen/third_party/pi0-quant`). Integrated into torchAO via
`Understanding-PI0/understanding_pi0/common/fp8_po2_quant.py`.

- **302 linears** quantized to fp8 (including Gemma expert with hidden_dim=720)
- **1 linear** skipped (lm_head)
- **Zero int8 fallback** (no block_size constraint, unlike MX format)
- Scale = `2^floor(log2(amax / 256))` — fits NPU E8M0 scale registers
- All attention, RoPE, RMSNorm fixed to bf16 (source edits in
  `smolvlm_with_expert.py`, not monkey-patches)
- Conv2d patch embedding also quantized to fp8

## NPU Compiler Passes

The `npu_ucb` target activates the NPU plugin (`--iree-plugin=npu`) which runs
three custom passes:

| Pass | Phase | Purpose |
|------|-------|---------|
| `FoldFP8ScalesAroundContractions` | Preprocessing | Fold QDQ chains into matmuls: bf16 inputs → fp8 inputs |
| `FuseF32IntermediateConversions` | Pre + Post global-opt | Collapse `fp8→f32→bf16` into direct `fp8→bf16` |
| `DemoteF32ToBF16` | Post global-opt | Convert all remaining f32 to bf16 |

NPU ISA lowering is disabled (`--iree-npu-enable-npu-lowering=false`) — the
output is standard linalg ops with fp8/bf16 types for kernel extraction.

## AutoComp Kernel Generation

AutoComp (`third_party/autocomp`, branch `main`) generates NPU ISA kernels
via LLM-driven search with cycle-accurate simulation feedback.

### Setup

```bash
cd third_party/autocomp && pip install -e ".[tapeout]"
```

API key in `autocomp/common/keys.py` (Google Gemini via `GOOGLE_API_KEY`).

### Harnesses

13 tile-level harnesses in `harnesses/tapeout/{id}_{name}_test.py`, one per
unique kernel type. Each defines 32×32 tile inputs, DRAM layout, and golden
output. Generated by `benchmarks/SaturnNPU/scripts/generate_autocomp_harnesses.py`.

### Running

```bash
# Single kernel
python benchmarks/SaturnNPU/scripts/run_autocomp_all_kernels.py \
  --prob-id 0 --model "gcp::gemini-2.5-pro"

# All kernels
python benchmarks/SaturnNPU/scripts/run_autocomp_all_kernels.py
```

### Hand-writing vs. autocomp

Five kernels kept regressing in autocomp search. Root-causing them revealed
issues that are *structural*, not search-quality problems:

- **Hardware layout convention.** `vpack.bf16.fp8` consumes its two bf16
  inputs as left/right column halves (`cat([m_lo, m_hi], dim=1)`) — the same
  layout MXU produces natively. A row-major 32×32 bf16 tile in DRAM cannot be
  vloaded into the right shape with a single DMA. The fix is to present
  inputs already split at the harness level, matching production flow.
- **Default ERF = 0.** `vpack`/`vunpack` multiply by an ERF scale; without an
  explicit `seli rd=k, imm=1` the output is zeroed. Autocomp consistently
  missed this hint across 8+ iterations.
- **Golden precision.** The simulator's reductions promote to fp32 then cast
  to bf16. Goldens computed entirely in fp32 produced spurious mismatches at
  the 0.03 level. Fixed by computing goldens stepwise in bf16.
- **DMA flag discipline.** `dma.config` and `dma.load` on the same channel
  without a `dma.wait` in between trip an "Flag N already set" assertion.

Two latent `npu_model` simulator bugs were also surfaced while writing
requant:

- `vpack.bf16.fp8` called `write_mrf_fp8(quantized_fp8)` where the setter
  asserts `dtype == uint8` — simulator threw. Missing `.view(torch.uint8)`
  (the companion `vmatpop_fp8_acc_mxu1` already did this correctly).
- `write_mrf_fp8` itself used `self.mrf[vd].view(float8_e4m3fn)[:] = u8`,
  which PyTorch *value-casts* (uint8 byte 173 → fp8 +176.0, stored as 115)
  rather than byte-copying. Fix: view target as `uint8`.

Both are patched locally in `third_party/npu_model` and explain why every
autocomp run that touched `vpack` silently failed its golden check.

After fixing the harnesses and simulator, the stuck kernels were
straightforward: softmax 196 cy, rms_norm 258 cy, reduction_sum 110 cy,
requant 107 cy — all with max diff 0.0.

### Harness conventions (production-aligned)

To match the MXU's natural data layout, kernel harnesses present bf16 tiles
**pre-split into 32×16 left / right halves in DRAM**:

- `DRAM[0x0000..0x0400]` — left half (32, 16) bf16
- `DRAM[0x0400..0x0800]` — right half (32, 16) bf16

Reductions (row-sum, row-max, rms) produce a **broadcast output**: (32, 16)
bf16 where each row is the per-row scalar repeated. This is exactly what the
downstream broadcast ops consume, so no reshape is needed between kernels.

Constants (`1/N`, `eps`, GELU coefficients) are **DMA-preloaded** into DRAM
as filled 32×16 bf16 tiles. This avoids the scalar-store constant construction
that tanked autocomp's first gelu at 796 cy (dropped to 337 cy once
constants were preloaded).

### Tiled kernels

For performance, autocomp also generates **tiled kernels** with DMA pipelining
(harness `30_tiled_matmul_2x1_test.py`). These overlap DMA loads with MXU
compute across consecutive 32×32 tiles.

## NPU Simulator Integration

The npu_model simulator (`third_party/npu_model`) validates generated kernels:

```bash
cd third_party/npu_model
uv run scripts/run.py --program MatmulProgram --max-cycles 5000
```

Each autocomp kernel is a `Program` class with `instructions`, `memory_regions`,
and `golden_result`. The simulator runs cycle-accurate execution and compares
output against the golden PyTorch reference (rtol=1e-2, atol=1e-2).

## Architecture

```
PyTorch (SmolVLA)
  → FP8 Po2 Export (fp8_po2_quant.py)
  → IREE Compilation (iree-compile + NPU plugin passes)
  → Kernel Extraction (21 matmul + 43 type_conv + VPU ops)
  → AutoComp (LLM generates NPU ISA for each kernel type)
  → npu_model Simulation (cycle-accurate verification)
```
