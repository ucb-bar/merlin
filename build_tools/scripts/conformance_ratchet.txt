# gemmini — NEW REQUIREMENT FROM RECOVERED EVIDENCE, not new debt.
#
# `model_coverage.load_module` never applied the multi-result normalizer that `parse_mlir_text` has
# always applied, so five captures -- `bitvla` and four `smolvla` bundles -- failed to parse and were
# recorded as unreadable in every target's spec. The requirement was derived from 27 captures; it is now
# derived from 32, and the spec no longer carries an `unreadable` note. These three obligations are what
# those five models actually demand and nothing had been asked to cover before.
#
# ⚠️ THE TWO `attention` LINES ARE A DOUBLE-COUNTED REQUIREMENT, not a corpus gap, and the distinction
# is why they are recorded here rather than fixed with a capsule. `host_lane` derives every
# (family, dtype) pair the captures contain and the manifest does not admit; `host_only` derives every
# family the manifest admits at NO dtype. A family with no admitted dtype satisfies both, so `attention`
# is required once as a host-only family AND once per dtype as a host-lane pair.
#
# `corpus_synth` resolves that by delegating: its host-lane loop skips a family the narrow host-only
# axis already carries, and emits `SY_host_only_attention` instead. That is the right call -- one
# capsule proving a family never reaches the accelerator is the evidence, and a per-dtype restatement
# is not additional. But the requirement still counts the pairs, so they can never be covered, and the
# gate reads a permanent gap where the corpus is actually complete.
#
# The real fix is in `conformance.host_lane_cells`: a family required as wholly host-only should not
# also be required per dtype on the host lane. That narrows a derived requirement, which wants its own
# change and its own argument, so these sit here until then. `SY_host_lane_attention_bf16` used to
# cover one of them incidentally and was pruned when the requirement was re-derived, which is what
# surfaced the double count.
#
# `movement/bf16` below is a genuine gap of the ordinary kind.
#
# `attention/f32` and `movement/bf16` are HOST-LANE obligations: work the compiler must place on the
# host because this target's datapath does not admit it. The int8 captures that previously drove the
# requirement carry neither at those widths; the VLA captures do. A compiler that quietly accelerates
# one of them is wrong in a way no accelerator pass-rate can see, which is the whole point of the
# negative lane -- so these want a host-lane capsule each, of a shape the synthesizer already builds
# for other dtypes.
gemmini host_lane:attention/f32
gemmini host_lane:attention/bf16
gemmini host_lane:movement/bf16
