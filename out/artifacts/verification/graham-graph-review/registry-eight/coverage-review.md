# Review of the eight registered common transformations

This audit accounts for the eight kinds in the pinned common-pipeline registry. It finds a substantial difference between **a transformation being implemented**, **its local mathematical obligations being checked**, and **a validator proving preservation of the complete modeled boundary**. The available evidence does not establish one approved, composed correctness claim covering every implemented input domain of all eight kinds.

The detailed matrix is [coverage.csv](coverage.csv); the next actions are in [gaps.md](gaps.md). There are 34 review rows: the implemented rewrite forms plus selected domain partitions that change which validator can apply. This is a useful partition of mechanisms and scope, not an exhaustive enumeration of shapes, widths, loop depths, parameter combinations, or possible programs. Row counts are not proof counts or a coverage percentage.

**Why normalization and integer simplification need special attention.** In `verify_pipeline_change`, the shape witness selects one of these generated statements:

```lean
∀ (α : Type) (value : α), id value = value
(4 : Nat) = 4  -- representative static extent
```

Both are valid statements. Neither contains the actual before/after memref program. Correctly recognizing the cast, resolving the dimension, preserving the descriptor interpretation, replacing SSA uses, and preserving surrounding observations are carried by trusted Python and operation semantics. Whole-buffer hashes identify which program was submitted; they do not turn these propositions into whole-program preservation theorems.

The integer route is more substantive locally: it checks actual fixed-width arithmetic or a universally quantified neutral-element equation. It still lacks a demonstrated complete-context theorem tying all of the actual rewrite to the graph language. The newer scalar graph normalizer preserves pure expression structure and is not automatically an arithmetic identity prover. Older `MerlinVerify` numerical/integer proofs have a different identified semantics and cannot be borrowed without an explicit bridge. Producer integer simplification has no explicit 256-bit upper bound, while the scalar exporter and newer scalar pure-node domain use widths 1..256.

**What the scalar graph proof adds.** `lean_graph_state_scalar_capture.project` accounts for the function roster, interfaces, metadata, lexical SSA operands, captures, loop carries/yields, returns, and retained opaque descriptors. `emit_query` places both actual programs in Lean. `Merlin.GraphState.Scalar.check_sound` concludes `Preserves`, which quantifies over a common model and correctly sized inputs and equates `evalProgram` results. A result contains the returned vector and world, or an error and its terminal world. Private SSA stacks need not agree.

Pure primitives are deterministic total functions without access to the world. Retained opaque operations may fail, but use the same descriptor meaning and successful-result arity contract on both sides. Loop control is a common finite iteration-sequence interpretation, not a proved raw-SCF index implementation. These premises explain why removing unused work or moving it out of an empty loop is allowed in this model. They do not prove actual primitive fidelity or poison freedom.

Fresh CSE in a program containing an internal call is produced successfully but refused by this projection. Fresh LICM with runtime stride is also produced successfully but refused. Those rows cannot inherit the qualification of the narrower scalar packet. The same caution applies to CFG and unknown-region contexts, which the producer and graph intake handle differently.

**Loop proof strength and domain.** The segmentation and unrolling roots relate complete executions under a shared partial body relation, including exact original-body iteration order and final carried/state values. This is materially stronger than partition arithmetic. However, the relation records complete executions; it does not by itself compare first errors, their terminal worlds, or divergence. That is a different claim from the scalar `Outcome` equality.

The Python decoders bind complete raw syntax and unchanged context, then Lean checks control, clone, carry, and context data. The raw operation-to-body interpretation remains trusted. Fresh nested segmentation and unrolling examples pass the producer's structural checks but are refused by the retained graph projection modes. Multiple changed loops are also excluded by the decoders' exact-one-boundary guards. Dynamic/negative bounds, metadata, index-width limits, and unchanged factor/tile-one cases must be reported according to the actual route; an unchanged case is not positive evidence for a rewrite.

The existing `GraphLoopsUnroll.Composition.checked_composed` requires a compatible **no-tail bulk** unroll and segmentation of that same bulk body. It installs the grouped original-body interpretation and preserves the original-body log/state. It does not prove arbitrary unroll→segment combinations or silently connect to the scalar error-preserving evaluator.

**Buffer reuse and allocation.** The newer memory proof relates all live initialized logical cells to the physical slots and preserves possible complete public outcomes. It supports explicit initialization, loads/stores/dimensions, and retained public actions. It does not equate allocation history, private pointers, failure categories, or divergence traces.

Allocation/free are total, private, and unobservable in the admitted model. The retained report documents an actual case whose peak live storage increases from 8 to 16 bytes after reuse; a finite capacity-8 allocator distinguishes source and target. This audit did not rerun that resource experiment. The premise must remain visible even if a lifetime theorem and a possible-outcome theorem both pass.

The producer also accepts domains outside the retained decoder. Fresh examples establish this for i128 elements, rank-zero memrefs, nondefault memory space, and dynamic later private accesses after full initialization. Every one changes successfully and is refused by the newer reuse projection. The narrower mode requires one allocation-owner block, nonempty rank, default space, i8/i16/i32/i64, static valid later access coordinates, and signed32/64 context. Multiple allocation scopes and other source-domain differences remain explicit scope limits, not inferred coverage.

**Dependency scheduling has two distinct proof routes.** The producer derives SSA edges, including captured operands, and orders all effectful/unknown operations conservatively. It can move independent pure operations without changing that effect order. The old broker nevertheless only exports one defined scalar function with modeled integer operations. Its generated `merlin_transform` equates the complete return vector for every argument bit pattern. This is a whole-function result within that domain; it should not be mislabeled merely a local arithmetic lemma.

The newer route derives an exact operation roster, order and complete effect-cell projection from the actual modules. `GraphState.check_sound` checks an adjacent-exchange sequence reaches exactly the target order, and uses `StateEffects.preserveExchanges`. Its `Preserves` quantifies over actions satisfying totality, read-locality and write-frame laws, plus arbitrary sequential prefix/suffix contexts. Actual resource identity, complete effects, aliases, and any memory-definedness assumptions remain external obligations.

Fresh observations distinguish the routes: a pure single-function permutation emits both projections; a selected entry with another unchanged function is refused by the old exporter but accepted by the newer projection; an undeclared opaque observer is conservatively retained by the producer but refused by both inspected default projections. A reviewed effect declaration could admit some additional operations in the newer route, but an arbitrary unknown or partial operation cannot inherit that guarantee. Standalone effect-checking APIs and configuration-hoisting proofs are not evidence that `verify_pipeline_change` automatically invokes them.

**Host enforcement and composition remain separate.** `apply_common_pipeline` dispatches actual changes through an externally supplied verifier and, outside `plan_only`, calls the old broker's `accepted_pipeline_receipt`. That broker checks a live process-local completion bound to source/target bytes, domain, scope, semantics and toolchain. Saved JSON and a successful callback are not sufficient. The newer standalone graph checkers are not automatically this completion type or this admitted path. This is an integration distinction, not an assertion that the old host accepts arbitrary unchecked changes.

Within the eight kinds, there is an exact scalar CSE/DCE→LICM composition and a conditional no-tail unroll→segment composition. These use different semantic relations. A shared middle hash cannot equate a total state action, a partial body relation, possible complete public outcomes, and explicit error/terminal-world outcomes. The newer four-pass and memory-SCF work addresses real missing bridges, but its source presence is not completed qualification.

**Reassessment before expanding the inventory.** The next useful step is to resolve the claim boundary within these eight. Normalization and integer simplification need a clearly stated whole-context justification or a deliberately narrower trusted-reconstruction claim. The named raw qualification bundles should be recovered before independently confirming the historical loop/memory/scheduling qualification claims. Producer-only variants should be explicitly excluded from a narrow claim or receive their own extended validator; they should not inherit a family label. Then select which compositions and host-admission routes the paper actually needs. The broader scheduling/fusion/transfer/storage inventory can follow as a separate denominator without obscuring these already-demonstrated gaps.
