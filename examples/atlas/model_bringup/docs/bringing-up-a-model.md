# Bringing up a model on Atlas

For Agustin, Jeremy, and Loren bringing up Gemma2 or pi0, begin with [Start here for a new model](#start-here-for-a-new-model), then use the TinyLlama and SmolVLA examples below. [atlas-kernels](https://github.com/ucb-bar/atlas-kernels/tree/feat/kernel-library) owns kernel generators, shared references, and model coverage; atlas-mlir owns the compiler backend and generic host ABI; Merlin owns the model runtime, builders, tests, and QEMU tooling in `examples/atlas/model_bringup/`. The external compatibility view supplies the historical `third_party/atlas-kernels` layout from the independently selected library root. [Merlin comparisons](https://github.com/reed-nicolas/merlin/tree/atlas/sota-bringup-evidence/examples/atlas/comparisons) (Merlin [PR #55](https://github.com/ucb-bar/merlin/pull/55)) owns captures and hand-written model C providers; the TinyLlama full graph also has sources in Merlin `examples/atlas/model_bringup/tools/tiny_full/`. The separately pinned npu_model supplies instruction arithmetic and device execution. Keep checkpoint, input, source, program, toolchain, and ELF hashes with each result.

This is a hand-built bringup checked against pinned export inventories and npu_model; Merlin's semantic compiler and provider route is not integrated with these full-model builds.

## Two routes and their connection

Agustin's compiler route on `feat/atlas-model-compilation` takes PyTorch through Model2MLIR, `merlin-targetgen stage-capture`, Merlin's semantic compiler, Atlas virtual MLIR, `atlas-opt`, and `atlas-emit --program-json`, and generates C dispatch. See the branch's [memory and device lowering](https://github.com/ucb-bar/Merlin/blob/feat/atlas-model-compilation/docs/guides/model_memory_and_device_lowering.md), [C dispatch](https://github.com/ucb-bar/Merlin/blob/feat/atlas-model-compilation/docs/guides/dispatch_c.md), and [Atlas binding](https://github.com/ucb-bar/atlas-mlir/blob/feat/atlas-model-compilation/docs/native-merlin-binding.md). The established evidence at Merlin `62ab24eda` and atlas-mlir `ae8581f` covers small static authored workloads, with largest proven single program M×K×N = 128×512×128. It does not establish compilation of these complete models.

The model route in PR #26 and Merlin PR #55 uses PyTorch `torch.export` for the op and shape inventory, Merlin captures for real values, atlas-kernels Python generators for real device shapes, per-launch npu_model exactness, a hand-written host graph, a host ELF, and QEMU execution. FireSim packaging is a subsequent static step. The generators emit hand-scheduled assembly; translating that assembly to machine IR does not make their schedules or the host graph compiler-generated.

Agustin's route has three things ours lacks: its device programs are compiler-generated, which is the property the bringup ultimately needs; its C dispatch is generated; and its small kernels have run on the standalone `AtlasCore` RTL. Our route has run no full model ELF on RTL: only small test ELFs (a 25-launch smoke test, the ResNet50 max pool and patch gather, and the SmolVLA fc1 epilogue) passed VCS RTL simulation, and its model-level device evidence is npu_model execution plus a QEMU replay with captured device replies. The one concrete bridge so far is atlas-mlir [PR #44](https://github.com/ucb-bar/atlas-mlir/pull/44), which moves our traffic-reuse ideas (row-local VMEM operand caches, accumulator retention, compact-compilation retry, and scratch-slot sharing) onto his tip `ae8581f`. PR #26 forks from `7b7a0981`, 10 commits behind his base, and has 8 conflict hunks with his atlas-mlir branch (runtime `atlas_host.c` and `atlas_host.h`, CMake, and docs); Merlin #55 merges cleanly with his Merlin branch.

The gate commit `0c0edf7` (the code gate; later commits change only docs and tests), with atlas-kernels `6123bef` and Merlin `64264283`, compared 1,589 distinct programs and 1,487,694 words against both npu_model's assembler and the binaries embedded in the 16 ELFs: all matched, with 13 `verified` and 1,576 `stream-verified`. The builders still default to the assembler; the explicit wrapper below adds an opt-in enforcing compiler comparison gate around that path and returns the assembler-produced program. At that commit all 16 ELFs rebuild byte-identical, CTest passes 221 of 232 with the same 11 failures as `8259b83` (9 missing-model environment failures and 2 test defects; the later fixes bring a build of `76e10bf` to 223 of 232, and the 9 left need npu_model on the Python path), and atlas-kernels `make test` runs 164 tests with no failures and no skips (with PyYAML and `ATLAS_MLIR_BIN` set; 34 skip without them). These are recorded integration results, not executions performed by this documentation update.

The intended connection is to select these library kernels behind the compiler's provider adapter, by op, shape, and arithmetic policy. On Agustin's branch the seam is `AtlasApplicationAdapter.plan`, `compile_region`, and `export_region` in `python/atlas_mlir_native/application.py`. Region matching, a named precision policy, weight-window handling, and a merged host runtime remain integration work. His resident window is at most 1 MiB; a TinyLlama 2048×5632 FP8 weight matrix contains 11,534,336 bytes before metadata.

This follows the Radiance separation: RTL in radiance, kernels and references in radiance-kernels, compiler in radiance-mlir, and experiments in Merlin. Merlin's [Radiance materializer](https://github.com/reed-nicolas/merlin/blob/atlas/sota-bringup-evidence/examples/radiance/phase1/kernel_library/materialize.py) exports a pinned kernel commit with `git archive`; its adjacent `selection.yaml` maps op, dtype, and shape rules. Historically, atlas-mlir consumed atlas-kernels as a pinned submodule, because byte-pinned receipts import the generators by bare name. The split removes that compiler gitlink; the current execution view uses an independent `KERNELS_ROOT` admitted at `f9be64642907814caad500afd1e6fd6ad4bfcd48`. Merlin #55 adds the Atlas counterpart of the Radiance materializer, [`examples/atlas/phase1/kernel_library/`](https://github.com/reed-nicolas/merlin/tree/atlas/sota-bringup-evidence/examples/atlas/phase1/kernel_library), whose `selection.yaml` is generated from the `kernel.yaml` manifests and checked against the coverage data; it is disabled by default. Those historical pins named atlas-kernels `ec0178528d367ebc3367dfe34ed9876d462f95e9`; the historical `MERLIN_ATLAS_MLIR` check compared the checkout's HEAD gitlink. Current bringup setup selects the independent library root rather than maintaining a compiler submodule. The coverage mapping records where the qualified builds put work; it is not that compiler selector. The bringup tooling is copied to Merlin `examples/atlas/model_bringup/`, and `examples/atlas/comparisons` keeps its current path.

## Start here for a new model

The first steps for a new model need no captures and no retained inputs: a PyTorch model, a loader for it, atlas-kernels, npu_model `47b8599d8ffbe5ddd96059ffe2b5be2427a410f5`, a Python 3.14 interpreter with torch and NumPy for npu_model, and, for the compiler tier column, `atlas-opt` and `atlas-emit` built as the [compiler Build section](https://github.com/ucb-bar/atlas-mlir/blob/787ad51/README.md#build) describes. Without `--atlas-mlir-bin` the bench runs on npu_model's assembler alone. npu_model is at `git@github.com:ucb-ee194-tapeout/npu_model.git`, which needs access to the ucb-ee194-tapeout GitHub organization. Run the commands in the atlas-kernels section [Starting a new model](https://github.com/ucb-bar/atlas-kernels/tree/feat/kernel-library/README.md#starting-a-new-model): they export every op and shape with `torch.export`, place each op on a kernel family or list it as unmapped, and run every distinct Atlas launch at the model's real shapes on npu_model.

The result is a `MODEL-BENCH.md` table. Read it for `no-variant` rows, where a kernel family exists but its generator rejects the shape, and for unmapped rows, where no family or host code covers the op. Three committed tables show the format: [TinyLlama](https://github.com/ucb-bar/atlas-kernels/tree/feat/kernel-library/coverage/examples/tinyllama/MODEL-BENCH.md), [SmolVLA](https://github.com/ucb-bar/atlas-kernels/tree/feat/kernel-library/coverage/examples/smolvla/MODEL-BENCH.md), and [causal_decoder](https://github.com/ucb-bar/atlas-kernels/tree/feat/kernel-library/coverage/examples/causal_decoder/MODEL-BENCH.md). The causal_decoder table, for Merlin's small 8-token decoder, shows the limits a new model meets first: its head-dimension-8 attention stays unmapped because the family admits dimensions 64, 128, and 256. Its padded 32x32 RMSNorm does have a streamed variant and passes the model bench; the fused epilogues and residual adds report `no-variant`. The [shape-coverage bench](https://github.com/ucb-bar/atlas-kernels/blob/feat/kernel-library/coverage/examples/shape_coverage/README.md) tests representative wider attention and RMSNorm shapes, but does not qualify Gemma2 or pi0 model execution. Step 4 gives the focus-model bench results. The later steps (real-value capture, qualification, host graph, ELF, QEMU, and FireSim) need the inputs below.

## Worked sequence

Commands below run from the verified external execution view (`cd "$VIEW"`) unless a different repository is named. Variables name physical absolute paths to independent checkouts, authenticated external inputs, or fresh outputs; use the interpreter and pinned packages required by each linked runbook. `MODEL47` means unmodified npu_model `47b8599d8ffbe5ddd96059ffe2b5be2427a410f5`; `MODEL9` means `9e6313bddecb8ba936206eb347f5cd4e5335282c`. Native PyTorch capture, instruction execution, and host replay can require different Python environments. Use the explicit library root and view setup in the [model bringup instructions](../README.md#build); compiler builds follow the separate [compiler Build section](https://github.com/ucb-bar/atlas-mlir/blob/787ad51/README.md#build).

### 1. Inventory the executed ops and shapes

These commands run in atlas-kernels (`cd "$KERNELS"`; return with `cd "$ATLAS"`). Follow [coverage regeneration](https://github.com/ucb-bar/atlas-kernels/blob/feat/kernel-library/coverage/COVERAGE.md#regenerate) with the exact checkpoint and input used by the capture:

```sh
cd "$KERNELS"
PYTHONPATH="$TINY_PACKAGES" "$TINY_PYTHON" coverage/export_ops.py tinyllama --checkpoint "$TINY_CHECKPOINT" \
  --corpus "$TINY_CORPUS" --out "$MODEL_OUTPUT_ROOT/coverage/tinyllama" --fixture "$MODEL_OUTPUT_ROOT/coverage/fixture/tinyllama.json"
"$SMOL_PYTHON" coverage/export_ops.py smolvla --policy "$SMOL_POLICY" --backbone "$SMOL_BACKBONE" \
  --observation "$SMOL_OBSERVATION" --out "$MODEL_OUTPUT_ROOT/coverage/smolvla" --fixture "$MODEL_OUTPUT_ROOT/coverage/fixture/smolvla.json"
python3 coverage/build_table.py --out "$MODEL_OUTPUT_ROOT/coverage" \
  --inventory "tinyllama=$MODEL_OUTPUT_ROOT/coverage/fixture/tinyllama.json" \
  --inventory "smolvla=$MODEL_OUTPUT_ROOT/coverage/fixture/smolvla.json"
cd "$ATLAS"
```

`torch.export.export(strict=False)` yields 4,540 ATen records for TinyLlama and 18,923 for SmolVLA; committed fixtures aggregate these into 227 and 392 rows. It checks structure, shapes, and dtypes with fake tensors, not numerical values. The coverage guide names the checkpoint revisions, packages, input pins, and optional `--capture-receipt` cross-check. For a new model, add its loader and placement rules rather than editing the fixture by hand.

### 3. Map every op to a kernel or host operation

Use atlas-kernels `coverage/mapping.yaml` and `coverage/build_table.py` for both models. In atlas-kernels (`cd "$KERNELS"`), run `python3 coverage/build_table.py --out "$MODEL_OUTPUT_ROOT/coverage" --check-cites "$ATLAS" "$MERLIN" "$KERNELS"` to check citations against the integrated repositories. Start kernel additions with [Adding a kernel](https://github.com/ucb-bar/atlas-kernels/blob/feat/kernel-library/README.md#adding-a-kernel), the family's `kernel.yaml`, and its `gen.py`. Reuse needs matching shape, layout, dtype, scale policy, padding, and arithmetic order, not only an op name.

TinyLlama maps 465 logical projection calls, 66 attention launches, and 132 RMSNorm launches. SmolVLA maps 1,421 logical projection calls, 200 attention launches, and 24 fused fc1 calls. Logical calls and physical panels differ: SmolVLA has 2,715 projection panels. TinyLlama's current kit has 1,038 launches; earlier projection-plus-attention documentation describes 906 before the 132 norm launches. Read [TinyLlama program checking](tiny-fast-build.md) and [Smol placement and admission](smol-full-host.md) for the device plan details.

The plans remain hand-written: `tools/smol_full_plan.py`, `tools/smol_attention_assets.py`, and `tools/tiny_full/capture_boundaries.py` encode model geometry and ordering. [test_model_coverage.py](../test/test_model_coverage.py) has the following scope. The test checks ordered projection tuples, Smol input dtypes, complete Tiny projection output shapes, and Tiny cache/logit geometry against pinned export fixtures. Attention batch, query and KV head counts, head dimension, query and key extents, mask tensor extents, and recorded insertion order are compared with production planning and admission geometry. Shared helpers retain the production geometry and insertion rules; Tiny projection admission fixes logical rows, panel widths, and cache batch before the complete exported tensor shapes are compared. Aggregated fixtures do not contain exact mask values, scalar causal flags, or complete producer/consumer graph edges, so those are not established by this test. It does not check host operations, fusion boundaries beyond the plan, or scale contracts. Separately, `build_table.py` (`REQUIRED_LAUNCHES` and `launch_failures`) fails unless the export-derived counts equal the qualified kit counts, which are 465 projection calls, 66 attention launches, and 132 RMSNorm launches for TinyLlama, and 1,421 projection calls, 200 attention launches, and 24 fused fc1 calls for SmolVLA. Those count checks do not establish C graph or arithmetic correctness.

### 4. Check kernels at the actual shapes

In atlas-kernels (`cd "$KERNELS"`), with `ATLAS_MLIR_BIN` exported, run `make test PYTHON="$MODEL_PYTHON" NPU_MODEL="$MODEL47"`; at `6123bef` it runs 164 tests with no failures. The library's [family documentation](https://github.com/ucb-bar/atlas-kernels/tree/feat/kernel-library/kernels) identifies each generator, tests, and golden references. TinyLlama's launch executor is described in [attention execution](../tools/tiny_full/ATTENTION_EXECUTION.md); SmolVLA's small real-model check is `tools/smol_capture_smoke.py`, with the full command in [Smol capture](smol_attention_capture.md#capture-and-small-original-model-check).

Compare complete output bytes and preservation regions with npu_model RTL numerics, using the real padded shapes, scales, and DMA layout. Separately measure error against PyTorch or an FP32 reference. The standalone bench has 13 seeded synthetic cases across seven families: six have independent arithmetic goldens and are bit-exact, seven have no independent golden, and all 13 timed outputs equal their functional outputs. See atlas-kernels `coverage/RESULTS.md` and each family's `reference.py` and `RESULTS.md`. These representative shapes do not qualify every captured launch or every staging path. Coverage FLOP share is not latency. Functional `ArchState` execution in `atlas_execution.py` does not measure Core cycles.

The model bench from [Start here for a new model](#start-here-for-a-new-model) covers every launch a model's coverage implies, at its real shapes, on seeded synthetic inputs. For TinyLlama, 26 distinct launches cover all 1,038 kit launches, and 13 of 13 launches that have an independent golden are bit-exact. For SmolVLA, 28 distinct launches cover all 2,915, and 23 of 23 projection launches are bit-exact. The derived launch counts equal the kits': 840 projection panels, 66 attention launches, and 132 RMSNorm launches for TinyLlama, and 2,715 projection panels and 200 attention launches for SmolVLA. Its cycles are npu_model model cycles, not RTL cycles.

With `--atlas-mlir-bin`, the bench uses an opt-in enforcing comparison gate around the assembler path: it encodes each generated launch with `atlas-opt` and `atlas-emit`, requires equal words, and records the tier. The wrapper returns the assembler-produced program. Recorded tiers are, for TinyLlama, 2 `verified` and 24 `stream-verified` of 26 distinct launches; for SmolVLA, 1 `verified` and 27 `stream-verified` of 28.

Every generation/check command below that assembles in process is explicitly wrapped. Inspect its backend receipt as well as its normal result: backend, verification mode, command and exit code, library/translator SHA-256, tool paths/versions/binary hashes, model commit, compiler source identity, per-program source/word hashes, tier, and diagnostics. Missing tools or unequal words fail. The wrapper hooks imports in the current process only; fresh Python subprocesses require their own wrapper. Every wrapped command passes `--min-tier stream-verified` and `--expect-min-programs N` before `--`, so a run that records fewer than N distinct programs, or any program below `stream-verified`, exits nonzero. Do not use `--no-verify` for qualification. The exhaustive integrated kit check covers 1,589 distinct programs; do not expect that count from every smaller command. Recorded switch runs cover 210 Tiny check programs, 850 for each Tiny fast variant, and 537 for Smol fast assets, with deduplication scoped to each run, and the commands below use those counts. Commands with no recorded count use `$EXPECT_PROGRAMS`: set it to the number of distinct device programs that run's own inventory must produce, never to the default of 1. No count is recorded for the TinyLlama export, the SmolVLA export, the SmolVLA host build, or the SmolVLA bundle check. Every wrapped run writes the number of distinct programs it encoded to `summary.programs` in its `--receipt` JSON (210 in the recorded TinyLlama check), which `python -c 'import json,sys; print(json.load(open(sys.argv[1]))["summary"]["programs"])' RECEIPT` prints, and `tools/tiny_full/check_programs.py` prints `unique_programs` for a TinyLlama assets directory (210 for the 1,038-launch kit's assets). Take the count from a reviewed run of the same profile and pass it from then on. A changed profile must define and check its own expected inventory. The `--expect-min-programs 210` check is a program census; census, encoding, and rebuild gates do not derive the model plan or host graph.

In the pinned atlas-kernels `ec0178528d367ebc3367dfe34ed9876d462f95e9`, `run --expect-min-programs N` counts distinct program texts and defaults to 1, `--min-tier` defaults to `stream-verified`, and `compile` takes the same minimum-tier option. `--no-verify` requires explicit `--min-tier encode-only`. The library's standalone bench rejects golden/timed mismatches and empty selections; its mandatory-category coverage checks and bias accounting give SmolVLA an Atlas FLOP share of 99.9158% (TinyLlama 99.9995%). The earlier 99.9320% SmolVLA share omits bias additions.

## Pins, timing, and remaining work

`third_party/atlas-kernels/lib/atlas_execution.py` enforces original47 for functional per-launch arithmetic, as described in [attention execution](../tools/tiny_full/ATTENTION_EXECUTION.md). The second pin, `9e6313bd`, is used by `tools/run_model_tile.py` and `tools/host_iss/model_device.py` for the persistent `npu_model.Core` behind QEMU MMIO. It uses `numerics="rtl"` and the `curve` DMA memory backend. `tools/host_iss/segment_boundary.py` requires that revision, backend, and curve digest for segment chains. These pins support different gates; a replay on the second pin does not replace qualification on original47.

The older host-RoPE F3-h0 total is 3,528,847,056 npu_model cycles from 730 D2 timing reuses, 106 F2 timing reuses, and 202 fresh original47 Core timings. The current synthetic-input bench totals 3,537,507,930 cycles using reused full-shape timing runs; see the [bench reconciliation](https://github.com/ucb-bar/atlas-kernels/blob/feat/kernel-library/coverage/examples/tinyllama/MODEL-BENCH.md#L105-L109). Core cycle counts are npu_model model cycles. QEMU host cycles, model device cycles, standalone RTL cycles, and FireSim target cycles measure different systems and must be reported separately. In particular, functional executor instruction counts and coverage FLOPs are not device latency. The compiler route's small-kernel standalone RTL evidence does not establish full-model RTL or FireSim timing. Per-kernel RTL cycles for the atlas-kernels families are future work; the standalone `AtlasCore` flows in [compiler hardware status](https://github.com/ucb-bar/atlas-mlir/blob/787ad51/docs/hardware-status.md) (an arcilator build driven through ModeLIR, and `CompiledProgramAtlasCoreDiagnosticTest` for whole compiled programs under Verilator) are the starting point.

The host graphs and device plan files are still hand-written. `build_table.py` checks the export-derived launch counts against the kit counts, and `test/test_model_coverage.py` checks the bounded plan geometry and ordering described above against pinned export fixtures. That test does not check host operations, fusion boundaries beyond the plan, or scale contracts. Program census, encoding parity, and byte-identical rebuild gates preserve the admitted artifacts; they do not derive these plans or host graphs. New observations and inputs need regenerated authenticated capture and boundary providers. Source-hash checks can reject historical receipts after source movement or edits; explicit relocation preserves hashes and does not authorize changed bytes. The compiler branch's `atlas_host` API has `ensure_loaded`, `invalidate_program`, `reset_completed`, and `set_clock`, while this bringup runtime has raw loading and launch ranges. That divergence must be reconciled before combining the routes.

The 1,576 timing-rejected programs were checked against all pending DMA ranges on every channel on original47: 0 hazards, 202,033,593 instructions, and 6,092,213 DMAs. This experiment used one input per program, 1,531 fast-mode and 45 full-mode executions, excluded host accesses, and did not model real RTL completion timing. Controls injected hazards and compared fast with full execution. It supports those executions, not a universal race proof.

The release timing verifier stops at its first violation. An uncommitted diagnostic-only build continued through all violations and found no issue-spacing, reservation, or fixed-latency violation. Its DMA diagnostics reflect per-block register reasoning that cannot prove loop-buffer disjointness and the restriction against DMA crossing block boundaries. Separately, the halt-after-DELAY rule is a genuine finding in 45 attention programs (25 TinyLlama, 20 SmolVLA): `delay 128; ecall` does not wait for the pad on RTL. Experiments found no outstanding work at halt, so results were unaffected. Dropping the pad or inserting a scalar guard changes words and is deferred pending requalification. Neither the diagnostic build nor this experiment upgrades these programs to timing-verified.

For Gemma2, begin by checking whether projection, RMSNorm, RoPE, gated epilogues, and attention families fit the exported layouts and arithmetic. Check attention masking, scaling, soft-capping, cache geometry, and normalization explicitly; the TinyLlama example does not prove them. For pi0, inventory vision, text, action, attention, and denoising/control work independently before borrowing SmolVLA families. A new op or incompatible layout belongs in the coverage work list until a kernel or explicit host implementation and its checks exist.

Merlin's [held-out workload policy](https://github.com/reed-nicolas/merlin/blob/atlas/sota-bringup-evidence/examples/workloads/README.md) reserves TinyLlama, SmolVLA, and ResNet50 for headline validation. Keep these bringup captures, frequencies, and results out of capsule derivation and performance selection. Agree on the provider integration and experiment location before treating this hand-built coverage as compiler selection evidence.
